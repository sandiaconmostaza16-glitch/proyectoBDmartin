Modelo de datos Ruta

Base de datos del marketplace de autos usados Ruta: catálogo de vehículos, ubicación, usuarios y solicitudes de compra que confirma un asesor. Motor SQL Server, acceso desde el backend con SQL explícito y parametrizado, sin ORM.

Visión general

Qué hace la aplicación y qué reglas debe respetar la base

Resumen

Un cliente navega el catálogo, filtra, guarda favoritos, arma un carrito y envía una solicitud de compra. Un asesor la revisa y confirma el precio final; la compra no se paga en línea.

Reglas de negocio

Restricciones del negocio que el modelo y los objetos SQL deben garantizar.

  • RN1Cada auto usado es único (tiene patente). No hay stock de unidades iguales; el estado del auto reemplaza al stock.
  • RN2Un auto solo puede estar en una solicitud activa. Al solicitarlo queda reservado.
  • RN3El precio que vale para la solicitud es el del momento en que se envió.
  • RN4Solo un usuario con rol ASESOR puede confirmar o rechazar una solicitud.
  • RN5Una solicitud pendiente por más de 72 horas vence y el auto vuelve a estar disponible.
  • RN6Todo cambio de precio queda registrado, sin importar desde dónde se haga.

Decisiones de diseño

El porqué de cada elección. Es lo que más preguntan en una presentación.

Normalización hasta 3FN

1FN: "Palermo, Buenos Aires" se separa en Ciudad y Provincia. 2FN: en las PK compuestas cada atributo depende de la clave completa. 3FN: la provincia depende de la ciudad y la categoría del modelo, no del auto.

Marca y Modelo en tablas aparte

Si "Toyota" fuera texto en cada auto, alguien escribe "toyota" o "Toyta" y el filtro falla. Con catálogo y FK el valor existe una sola vez.

Categoría en Modelo, no en Vehiculo

Todo Corolla Cross es SUV. Guardarla en Vehiculo sería una dependencia transitiva (Vehiculo → Modelo → Categoria).

Transmisión con CHECK, Combustible con tabla

Transmisión tiene dos valores fijos. Combustible es filtro de la interfaz y puede crecer (GNC, híbrido enchufable).

El carrito no tiene cantidad

Cada auto es único (RN1). La PK (UsuarioId, VehiculoId) garantiza que cada auto aparezca una vez por carrito.

La cuota no se guarda

Depende del precio y del plan. Si se guardara y cambia el precio, quedaría mal. Se calcula con fn_CuotaMensual.

PrecioAcordado sí se guarda

No es redundancia: es la foto del precio al momento de la solicitud (RN3). Si el precio cambia mañana, la solicitud de ayer no cambia.

Sin columna Total en la solicitud

El total es la suma de los detalles; se calcula en vw_SolicitudesResumen. Guardarlo podría desalinearse.

Rol como columna con CHECK

Tres roles fijos sin atributos propios. Si los permisos fueran configurables, se pasaría a tablas Rol y Permiso.

"El asesor debe tener rol ASESOR" va en un SP

Un CHECK solo mira la fila actual y no puede consultar otra tabla. RN4 se valida en sp_ResolverSolicitud.

Los autos no se borran

Un auto vendido aparece en solicitudes históricas. Se usa Estado PAUSADO o VENDIDO (borrado lógico).

Vistas

vw_SolicitudesResumen

Pantalla: panel del asesor

Solicitud, cliente, plan, cantidad de autos y total calculado con SUM(PrecioAcordado).

Función

fn_CuotaMensual(@Precio, @Cuotas, @Tasa)

Usada por vw_CatalogoVehiculos

Cuota fija con sistema francés: P · i / (1 − (1 + i)^−n); si la tasa es 0, P / n. Con 48 cuotas al 2,4 % mensual, un auto de $28.900.000 da ~$1.020.000, igual que la tarjeta del mockup.

Ver SQL
CREATE OR ALTER FUNCTION dbo.fn_CuotaMensual
    (@Precio DECIMAL(14,2), @Cuotas SMALLINT, @Tasa DECIMAL(6,4))
RETURNS DECIMAL(14,2)
AS
BEGIN
    IF @Cuotas IS NULL OR @Cuotas <= 0 RETURN NULL;
    IF @Tasa = 0 RETURN @Precio / @Cuotas;
    RETURN @Precio * @Tasa / (1 - POWER(CAST(1 + @Tasa AS FLOAT), -@Cuotas));
END;

Por qué sp_CrearSolicitudCompra es una transacción

Son 4 operaciones. Si falla la tercera sin transacción, queda una solicitud sin autos reservados. Con transacción se hacen las 4 o ninguna (atomicidad).

Dos clientes compran el mismo auto a la vez

El SP lee los autos con UPDLOCK, HOLDLOCK. El segundo espera, ve el auto RESERVADO y recibe el error 50013.

El LIKE de la búsqueda no es inyección SQL

LIKE N'%' + @Texto + N'%' concatena el valor del parámetro, no arma una consulta para ejecutar. Inyección habría con EXEC('…' + @Texto).

Triggers

Se usan solo para lo que debe pasar siempre, venga de donde venga el cambio. La lógica de negocio principal queda a la vista en los SP.

trg_Vehiculo_CambioPrecio

AFTER UPDATE en Vehiculo

Cuando cambia el precio, guarda el anterior y el nuevo en HistorialPrecio.

Por qué trigger y no SPEl precio puede cambiarse desde un SP, el panel admin, un script o a mano. El trigger se ejecuta siempre (RN6) y alimenta "Bajó de precio".
Ver SQL
CREATE OR ALTER TRIGGER dbo.trg_Vehiculo_CambioPrecio
ON dbo.Vehiculo
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF NOT UPDATE(Precio) RETURN;

    INSERT INTO dbo.HistorialPrecio (VehiculoId, PrecioAnterior, PrecioNuevo)
    SELECT d.VehiculoId, d.Precio, i.Precio
    FROM inserted i
    JOIN deleted d ON d.VehiculoId = i.VehiculoId
    WHERE i.Precio <> d.Precio;
END;

trg_Vehiculo_SalidaDeVenta

AFTER UPDATE en Vehiculo

Cuando un auto deja de estar DISPONIBLE, lo saca de todos los carritos. Los favoritos se mantienen.

Por qué triggerUn auto sale de venta por varios caminos (otra compra, pausa del admin). Así nadie llega al checkout con un auto que ya no se puede comprar.
Ver SQL
CREATE OR ALTER TRIGGER dbo.trg_Vehiculo_SalidaDeVenta
ON dbo.Vehiculo
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF NOT UPDATE(Estado) RETURN;

    DELETE ci
    FROM dbo.CarritoItem ci
    JOIN inserted i ON i.VehiculoId = ci.VehiculoId
    JOIN deleted  d ON d.VehiculoId = i.VehiculoId
    WHERE d.Estado = 'DISPONIBLE' AND i.Estado <> 'DISPONIBLE';
END;
deleted tiene las filas antes del UPDATE e inserted las de después. Se usa JOIN y no variables porque el trigger se dispara una vez por sentencia, aunque el UPDATE toque muchas filas.

Cursor

sp_VencerSolicitudesPendientes recorre las solicitudes PENDIENTE con más de 72 horas y llama, una por una, a sp_ResolverSolicitud con estado VENCIDA (RN5).

Reutiliza la lógica existente

sp_ResolverSolicitud ya valida y cambia el estado de una solicitud y sus autos, pero recibe un solo @SolicitudId. Para aplicarlo a varias hay que recorrerlas. Así las transiciones de estado tienen una sola fuente de verdad.

Aísla errores

Cada llamada va en su propio TRY/CATCH. Si una solicitud falla, se cuenta y se sigue con las demás. Con un UPDATE masivo, un error revierte todo el lote.

Quién lo ejecuta

SQL Server Express no trae SQL Server Agent, así que lo llama el backend cada hora. En la demo: EXEC dbo.sp_VencerSolicitudesPendientes @Horas = 0;

Si preguntan: un UPDATE basado en conjuntos sería más rápido. Se acepta el cursor porque el volumen es bajo (decenas al día) y corre en segundo plano, donde importa la consistencia y no la velocidad.
Ver SQL
CREATE OR ALTER PROCEDURE dbo.sp_VencerSolicitudesPendientes
    @Horas INT = 72
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @SolicitudId INT, @Vencidas INT = 0, @Errores INT = 0;

    DECLARE cur_Vencidas CURSOR LOCAL FAST_FORWARD FOR
        SELECT SolicitudId
        FROM dbo.SolicitudCompra
        WHERE Estado = 'PENDIENTE'
          AND FechaSolicitud < DATEADD(HOUR, -@Horas, SYSDATETIME());

    OPEN cur_Vencidas;
    FETCH NEXT FROM cur_Vencidas INTO @SolicitudId;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        BEGIN TRY
            EXEC dbo.sp_ResolverSolicitud
                 @SolicitudId = @SolicitudId, @AsesorId = NULL, @NuevoEstado = 'VENCIDA';
            SET @Vencidas += 1;
        END TRY
        BEGIN CATCH
            SET @Errores += 1;
        END CATCH;

        FETCH NEXT FROM cur_Vencidas INTO @SolicitudId;
    END;

    CLOSE cur_Vencidas;
    DEALLOCATE cur_Vencidas;

    SELECT @Vencidas AS SolicitudesVencidas, @Errores AS Errores;
END;
